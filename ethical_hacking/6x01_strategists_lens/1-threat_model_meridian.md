## Framework Declaration
STRIDE

## Rationale
This migration introduces a high-risk trust boundary between the legacy mainframe, the AWS-based services, and the on-premises branch network, and STRIDE is well suited to cataloging those design weaknesses across identity, data movement, and service availability. The migration architecture diagram makes clear that the six-week dual-running period creates overlapping control planes, where a single compromised integration account or API path could affect both legacy and cloud workloads. The business context document emphasizes SOX, GLBA, and OCC obligations, which means confidentiality, integrity, and availability concerns are central business risks rather than purely technical concerns. The threat intelligence briefing on recent US financial-sector adversary activity also highlights impersonation, credential abuse, and service disruption as likely attack paths during transition states, which STRIDE maps directly to the most relevant categories. Compared with a purely adversary-technique model, STRIDE makes the architecture team’s engineering decisions more actionable by tying each concern to a concrete trust boundary and design control.

## Framework Selection Feedback
STRIDE is particularly valuable for Meridian because it forces the team to examine how identity, data, and administrative trust shift during the mainframe-to-AWS dual-running period, where those boundary failures are most likely to occur. The main limitation is that STRIDE is less precise than ATT&CK about adversary sequencing and campaign behavior, so it can underweight operational patterns such as credential stuffing, fraud workflows, or lateral movement once the environment is already compromised.

## Threat Model
### Scope and assumptions
- In scope: mainframe-to-AWS integration flows, AWS landing-zone services, on-prem branch connectivity, customer data transit, administrative access paths, and the six-week dual-running window.
- Out of scope: Luxembourg subsidiary systems and any non-Meridian customer or third-party infrastructure not explicitly included in the migration architecture and the RoE.
- Threat model anchored on the stated transition state: architecture is in migration, not steady-state production, and therefore trust boundaries and control redundancy are weaker than in a mature environment.

### Threat scenarios
1. Credential replay across the dual-running boundary: a stolen AWS service credential or reused mainframe token is used to access both migration staging and production data stores, enabling unauthorized data movement or transaction manipulation.
2. Event-stream poisoning: an attacker modifies a queue or API payload between the legacy system and the AWS integration layer, leading to manipulated account balances, bad reconciliation, or duplicate processing.
3. Admin-path abuse: a compromised developer or contractor workstation obtains elevated rights to the migration platform, then pivots into core data or branch connectivity infrastructure.
4. Availability denial during the migration window: a malformed batch file, recursive event loop, or unauthenticated API flood overwhelms AWS or on-prem systems and disrupts branch or customer operations.

### Key attack surface observations
- The identified attack surface is not a single application but a hybrid control plane spanning mainframe job orchestration, AWS APIs, and on-prem network segments during a temporary transition state.
- The highest-risk issue is not only a vulnerability in one component but the combination of identity reuse, shared secrets, and weak integrity checks across the migration boundary.
- Banking adversaries often prioritize data integrity, fraud enablement, and service disruption; these are directly mapped to the STRIDE categories above.

## Identified Findings
1. High — Shared or reused service credentials between legacy and AWS integration flows create a direct spoofing and privilege-escalation path during the six-week dual-running period. This is the highest-priority issue because it crosses the strongest trust boundary in the architecture and is consistent with financial-sector adversary behavior observed in the provided intelligence brief.
2. High — Data and event integrity controls are insufficient across the migration boundary, allowing tampering or replay of batch files, queue messages, or API payloads. The risk is elevated because the migration architecture indicates active parallel processing of legacy and new systems without a clearly verified attestation or checksum workflow.
3. Medium — Administrative privileges and secrets handling are too permissive across AWS and on-prem tooling, increasing the likelihood of an attacker obtaining operational dominance through a single compromised identity. This is materially important for SOX/GLBA/OCC-controlled environments because detection, evidence, and recovery become harder if break-glass access is not tightly constrained.
